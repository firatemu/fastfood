# Data Model and Database Principles

## 1. Database authority

PostgreSQL 18 is the canonical transactional database. PostGIS is enabled for geospatial service-area functionality.

## 2. ORM

Prisma ORM 7 is the canonical ORM. `schema.prisma` becomes the implementation source of truth for relational schema once implementation begins.

Prisma limitations around spatial types are handled through controlled migrations and parameterized raw SQL in the infrastructure layer.

## 3. Identifier policy

Primary persisted business entity IDs use UUIDv7 generated by PostgreSQL 18 through the database default `uuidv7()`. Prisma models map the UUID column explicitly. Application-generated UUIDs may be used for transient request/correlation identifiers, but core persisted primary keys do not switch generation strategy per module.

Human-readable numbers such as order numbers are separate from primary IDs.

Example:

- `order.id` = UUIDv7
- `order.orderNumber` = customer/staff-facing reference

Public APIs do not expose sequential database IDs as authorization mechanisms.

## 4. Money

All TRY monetary values are stored/calculated as integer minor units (kuruş). PostgreSQL financial columns use `BIGINT`; Prisma maps canonical money columns to `BigInt`. Public JSON APIs serialize canonical monetary minor-unit values as base-10 integer strings (for example `"12990"` = 129.90 TRY) so JavaScript clients never depend on unsafe 64-bit number serialization.

Example:

```text
129.90 TRY -> 12990
```

Do not use floating-point types for money.

## 5. Time

- database/application canonical timestamps: UTC,
- API timestamps: ISO 8601 UTC,
- business display timezone: `Europe/Istanbul`,
- branch schedules are interpreted using business/branch timezone rules.

## 6. Soft delete

Soft delete is used only when domain/audit requirements need retained records. Do not automatically add `deleted_at` to every table.

Financial/order/audit records are not physically deleted through ordinary product flows.

## 7. Optimistic concurrency

Mutable operational records that are prone to concurrent staff updates should include a version/revision strategy or transactional state guard.

## 8. Snapshots

Order records preserve purchase-time snapshots of catalog naming and prices. Historical orders do not join current catalog names as their only representation.

## 9. Constraints

Database constraints should enforce invariants that are safely enforceable at the database layer:

- not-null rules,
- unique keys,
- foreign keys,
- non-negative amounts where appropriate,
- valid uniqueness for idempotency keys,
- relationship constraints.

Application validation does not replace database constraints.

## 10. Indexing

Indexes must be planned for:

- order lookup by branch/status/time,
- customer order history,
- payment provider references,
- active courier assignments,
- loyalty ledger queries,
- audit queries,
- spatial service-area containment,
- unique idempotency keys.

Exact naming and Prisma mapping rules are defined in `35-DATABASE_PRISMA_CONVENTIONS.md`.
