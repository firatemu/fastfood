# Repository Bootstrap Acceptance Checklist

This checklist is the gate before feature-heavy implementation begins.

## Documentation

- [ ] Documents 00-49 exist in `fastfood-project-docs/` or the approved project documentation path.
- [ ] Root README links to documentation entry point.
- [ ] No contradictory stack decision remains.
- [ ] `32-IMPLEMENTATION_LOCK_IN.md` is treated as mandatory.

## Runtime/workspace

- [ ] Node 24 LTS pinned.
- [ ] pnpm 12 exact patch pinned through `packageManager`/Corepack.
- [ ] Turborepo 2 installed.
- [ ] `pnpm-lock.yaml` committed.
- [ ] workspace layout matches document 04.

## Applications

- [ ] `apps/api`
- [ ] `apps/worker`
- [ ] `apps/storefront-web`
- [ ] `apps/admin-web`
- [ ] `apps/customer-mobile`
- [ ] `apps/courier-mobile`

Each builds or boots to a minimal foundation state without business-feature placeholders pretending to be complete.

## Security foundation

- [ ] no hardcoded secrets
- [ ] auth module skeleton follows contract
- [ ] permission metadata pattern defined
- [ ] resource policy pattern defined
- [ ] rate-limit capability present
- [ ] structured logging redaction baseline

## Testing/CI

- [ ] Vitest configured
- [ ] Playwright configured for web
- [ ] Maestro directories/config strategy established for mobile
- [ ] GitHub Actions runs lint/type/test/build
- [ ] CI uses frozen lockfile

## Development runtime / no-deployment gate

- [ ] local Docker Compose (or approved equivalent) starts PostgreSQL/PostGIS, Redis, and MinIO
- [ ] development applications can boot locally without production infrastructure
- [ ] readiness/liveness endpoints are wired and testable locally
- [ ] no Coolify deployment configuration is required or created
- [ ] no staging/production deployment workflow exists
- [ ] no production credentials are required
- [ ] CI performs verification only and has no deployment step
- [ ] document 49 no-deployment policy is enforced

## Human-test readiness

- [ ] storefront/admin can be exercised in a local browser once their foundation exists
- [ ] mobile foundations can run on approved local simulator/emulator/development device flows
- [ ] development data can be reset and re-seeded deterministically
- [ ] errors/logs are visible enough to support human testing

## Gate rule

Phase 1 is accepted only when this checklist is satisfied and foundation checks pass. AI agents must not skip unresolved foundation failures merely to produce visible feature screens faster.
